### Section 2: Context (프로젝트 배경)

```
레이아웃: 2컬럼 (좌: 게임 소개, 우: NPC 소개) → 모바일: 세로 스택
```

**좌측 — 게임 소개:**
- 게임명: "회귀자는 탑을 오른다"
- 장르: 모바일 세로형 로그라이크
- 엔진: Unity 6
- 상태: 프로토타입 (APK 빌드 완료)

**우측 — NPC 소개:**
- 이름: 마타이오스
- 설정: 기억을 잃은 소녀 전사
- 역할: 플레이어 동반자, 스토리 진행 핵심

**NPC 행동 계약 (아래에 아이콘 + 한줄 리스트):**
1. 호감도 5단계(hostile/cold/neutral/warm/open)에 따른 어조 분리
2. 게임 세계관 밖 질문 차단 (BIW 규칙)
3. 스토리 진행(S0~S5)에 따른 기억 키워드 반응
4. S3 이후 정체성 혼란(fracture) 패턴
5. 항상 한국어 반말

**호감도 스펙트럼 비주얼:**
```
hostile(-100) ──── cold(-50) ──── neutral(0) ──── warm(50) ──── open(100)
   적대적            냉담           중립            따뜻함          신뢰
```
5단계를 그라데이션 바 또는 스텝 인디케이터로 시각화.

### Section 3: 문제 정의

```
레이아웃: 카드 3장 가로 배치 (모바일: 세로 스택)
디자인: 각 카드 상단에 아이콘 + 문제 번호, 하단에 설명
강조색: 붉은 계열 (문제 = 위험)
```

**P1 — 비용과 레이턴시:**
- 대형 API(Claude, GPT-4o)는 대화당 $0.01~0.03
- DAU 1,000 기준 월 $19+ (인디 게임에 부적합)
- 레이턴시 1~3초 (대화 흐름 깨짐)
- 오프라인 불가

**P2 — 한국어 일관성:**
- 소형 다국어 모델(Qwen2.5 등)은 학습 데이터에 없는 패턴이 들어오면 영어/중국어로 전환
- 622건 SFT로는 다국어 prior를 억제할 수 없음

**P3 — 캐릭터 행동 제어:**
- 호감도 5단계 × 스토리 6단계 × BIW 차단 = 동시에 통제해야 할 변수가 많음
- 소형 모델(0.5B~3B)의 제한된 용량으로 이 복잡도를 처리해야 함

**의사결정 트리 다이어그램 (Section 3 하단):**
```
NPC가 자유 입력에 반응해야 한다
 └─ 생성형 AI 필수
     ├─ 대형 API → ❌ 비용/레이턴시 (P1)
     └─ 로컬 추론
         └─ 소형 모델 (0.5B~3B) + 파인튜닝
             ├─ 한국어 유지? → ❌ 다국어 누출 (P2)
             └─ 캐릭터 통제? → ❌ 복잡도 (P3)
                 └─ ★ 이 세 문제를 동시에 해결해야 한다
```

### Section 4: 실패 기록 (×3)

```
레이아웃: 세로 타임라인 (좌측 선 + 우측 카드)
각 카드 구조: [시도] → [결과] → [원인] → [교훈]
색상: 실패 = 주황/빨강 계열
```

**실패 ×1: HCX-SEED 0.5B**
- 시도: 네이버 한국어 특화 모델. 한국어 성능에 기대.
- 결과: 완전 실패
  - GGUF 변환 시 가중치 매핑 오류 (hyperclovax 아키텍처 미지원)
  - Ollama 출력: 이름 "마타리오스", 성별 "남성", 마크다운 표 작성
  - Colab 직접 추론: BIW 차단 실패 ("서울 날씨" → 실제 날씨 정보 생성)
- 원인: 학습 자체가 안 됐을 가능성 (BPE 사일런트 실패)
- 교훈: **GGUF 호환 여부를 모델 선택 전에 확인할 것**

**실패 ×2: Qwen2.5-1.5B v6.1**
- 시도: LLaMA 호환, ChatML 네이티브, GGUF 지원. 조건 완벽.
- 결과: 부분 실패
  - 9건 테스트 중 4건(44%)에서 영어/중국어 출력
  - "서울 날씨 어때?" → 영어로 답변
  - "너 AI지?" → "人工智能。" 중국어 출력
- 원인: 622건 SFT로는 Qwen2.5의 다국어 prior를 덮을 수 없음
- 교훈: **다국어 모델 + 소량 단일언어 SFT = 언어 누출 위험**

**실패 ×3: Qwen2.5-1.5B v6.2 (데이터 증강 시도)**
- 시도: 시스템 프롬프트 한국어 강제 + BIW 거부 데이터 85건 증강
- 결과: 개선 없음 (여전히 44%)
- 원인: 데이터 증강으로는 구조적 문제(base 모델의 다국어 prior)를 해결 불가
- 교훈: **데이터를 늘려서 해결 안 되면 모델을 바꿔야 한다**

**BPE 토큰화 버그 하이라이트 (코드 블록):**
```
이 버그는 별도 강조 박스로 만들 것.

제목: "사일런트 실패 — loss가 0인데 에러가 안 나는 버그"

설명:
DataCollatorForCompletionOnlyLM에 response_template을 문자열로 전달하면,
BPE의 컨텍스트 민감성 때문에 사일런트 실패가 발생한다.

코드 비교:
독립 토큰화: "마타이오스: " → [..., 25, 220]     (공백이 독립 토큰)
문맥 토큰화: "마타이오스: …좋진 않아." → [..., 25, 4593]  (공백이 다음 문자와 합쳐짐)

결과: 콜레이터가 응답 경계를 못 찾음 → 모든 라벨 -100 → 학습 토큰 0개

해결: trailing space 제거 + 토큰 ID 리스트 전달 + 라벨 검증 셀 추가
```

### Section 5: 해결 — EXAONE 3.5 2.4B 전환

```
레이아웃: 3단 흐름 (리서치 근거 → 실행 → 검증)
색상: 녹색 계열 (성공)
```

**5-1. 리서치 근거 (논문/자료 3건):**

| 자료 | 핵심 인사이트 |
|------|--------------|
| Monolingual vs Multilingual IT (EACL 2024) | 단일언어 SFT가 해당 언어에서 더 높은 성능 |
| Fixed-Persona SLMs (arxiv 2511.10277) | 소형 모델 + 페르소나 고정 + 모듈형 메모리 → NPC 대화 |
| EXAONE 3.5 공식 문서 | 한국어가 1순위 학습 언어 (Korean-primary) |

결론: **한국어 prior가 강한 모델을 써야 구조적으로 다국어 누출이 감소한다.**

**5-2. 실행:**
- 베이스 모델: EXAONE 3.5 2.4B-Instruct (LGAI-EXAONE)
- 파인튜닝: QLoRA r=32, alpha=64 (v6 대비 2배 강화)
- 데이터: 622 → 697건 증강 (BIW 30, open 25, fracture 20 추가)
- 환경: Colab A100, transformers==4.46.3, revision="8e6fc27" 핀

**5-3. 검증 (5세트 26턴 테스트):**

| 지표 | Qwen2.5 v6.1 | EXAONE v7 | 변화 |
|------|-------------|-----------|------|
| 한국어 유지율 | 56% | **100%** | +44%p |
| BIW 차단 | 부분 | **100%** | 완전 |
| 호감도 어조 분리 | 미검증 | **정상** | — |
| Fracture 패턴 | 미검증 | **정상** | — |

**Before/After 비주얼:**

### Section 6: 아키텍처 — 전체 파이프라인

```
레이아웃: 중앙 정렬 다이어그램 + 아래 텍스트 설명
```

**아키텍처 다이어그램:**
```
┌──────────────┐     HTTP POST      ┌──────────────────────────┐
│ Unity Client │ ◄─────────────────► │ FastAPI 추론 서버         │
│ (C# Coroutine)│   localhost:8421   │ (transformers + EXAONE)   │
│              │                    │                          │
│ MataiosDia-  │   /chat (구조화)   │ merged_fp16/ 모델         │
│ logueClient  │   /raw  (프리)     │ MPS / CUDA / CPU          │
│              │   /health (상태)   │ 자동 디바이스 감지         │
└──────────────┘                    └──────────────────────────┘
```

**Ollama → FastAPI 전환 스토리 (짧게):**
- llama.cpp GGUF "변환기"와 "추론 엔진"은 별개
- 변환(convert_hf_to_gguf.py)은 성공, 추론은 EXAONE attention 미지원으로 실패
- 대안: Python transformers로 직접 추론하는 FastAPI 서버

**Unity 연동 2종:**
1. RemoteLLMProvider — 동기식, ILLMProvider 호환, 서버 불통 시 결정론적 폴백
2. MataiosDialogueClient — 비동기 UnityWebRequest 코루틴, 실제 게임용

### Section 7: 결과 + 교훈

```
레이아웃: 상단 지표 카드 4개 + 하단 교훈 리스트
```

**최종 지표 (stat cards 가로 4개):**
1. 한국어 유지율: `100%`
2. BIW 차단: `100%`
3. 학습 데이터: `697건`
4. 모델 크기: `2.4B`

**기술 스택 요약 테이블:**

| 레이어 | 선택 | 비고 |
|--------|------|------|
| 베이스 모델 | EXAONE 3.5 2.4B-Instruct | Korean-primary |
| 파인튜닝 | QLoRA r=32, alpha=64 | Colab A100 |
| 추론 서버 | FastAPI + transformers | MPS/CUDA/CPU 자동 |
| 게임 엔진 | Unity 6 (C#) | 코루틴 기반 비동기 |
| 데이터 | 697건 JSONL | 13개 task, 6개 스토리 단계 |

**5가지 교훈:**
1. 모델 선택이 데이터 품질보다 중요할 수 있다 — 622건으로 Qwen 다국어 prior 못 덮었지만, EXAONE에서는 697건으로 충분
2. BPE 사일런트 실패는 진짜 무섭다 — loss=0인데 에러 없음. 라벨 검증 필수
3. GGUF 변환 ≠ 추론 가능 — 변환기와 추론 엔진은 별개
4. trust_remote_code는 반드시 revision 핀 — HF 커밋 업데이트 시 호환 깨짐
5. Ollama가 안 되면 FastAPI로 우회 가능 — transformers 직접 추론은 느리지만 충분
